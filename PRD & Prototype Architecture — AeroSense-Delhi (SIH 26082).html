Product Requirements Document (PRD)

AeroSense-Delhi: Air Pollution–Weather Coupled Forecasting System (Delhi NCR)

SIH Problem Statement #26082 | MoES

Version 1.0 — Prototype & Architecture Blueprint

1. Executive Summary

Delhi NCR's winter pollution crisis is not a "weather problem" or a "pollution problem" in isolation — it is a coupled physical system. Cold, calm winter nights create atmospheric inversion layers that trap PM2.5 near the surface; that trapped PM2.5 blocks sunlight, further cools the surface, weakens vertical mixing, and lowers the Planetary Boundary Layer (PBL) — which traps even more pollution. Add regional stubble-burning smoke arriving on specific wind trajectories, and Delhi's AQI can swing from "Moderate" to "Severe" within 24–48 hours.

AeroSense-Delhi is a 72-hour, high-resolution, two-way coupled weather-chemistry forecasting system for Delhi NCR, built around a decision-support dashboard for MoES/CPCB/GRAP authorities.

The single most important architectural decision in this PRD — and the one that makes the system realistic to demo at SIH while remaining production-credible — is this:

The prototype runs entirely on a mock/synthetic data layer that is schema-identical to the real data sources (IMD, CPCB, MOSDAC/INSAT-3D, Sentinel-5P, VIIRS/MODIS fire data). All real data ingestion is isolated in one swappable module — the Data Source Adapter Layer — so that going from "demo mode" to "live mode" is a configuration change, not a re-architecture.

This PRD covers: problem framing, users, functional/non-functional requirements, full system architecture, the mock↔real data-swap design (the core engineering insight the team asked for), the prototype's actual build spec, APIs, database schema, tech stack, timeline, risks, and demo strategy.

2. Problem Statement (Recap)

Traditional AQI forecasting treats meteorology and pollutant dispersion as separate, one-directional pipelines. In Delhi NCR this breaks down because:

  • Weather → Pollution: Wind speed/direction disperses or concentrates pollutants; temperature inversion and low PBL height trap PM2.5/PM10 near the ground; calm winter nights worsen accumulation.
  • Pollution → Weather: Dense aerosol loading blocks solar radiation, cooling the surface, suppressing convective mixing, and further lowering PBL height — a positive feedback loop.
  • External shock: Regional stubble burning (Punjab/Haryana, Oct–Nov) injects large smoke plumes that travel into Delhi NCR depending on wind fields, and get trapped by inversions on arrival.

Mandatory scope (from the SIH problem statement), which this PRD maps directly to requirements:

B 72-hour high-resolution AQI forecast (PM2.5, O₃ priority)

3. Goals & Non-Goals

3.1 Goals (Prototype / SIH stage)

  • Demonstrate the full decision-support experience — forecast, inversion tracking, plume tracking, two-way coupling narrative, dashboard, alerts — end-to-end, using a working simplified coupled model.
  • Prove the architecture is real-data-ready: same interfaces, same schemas, same downstream logic will work unchanged once WRF-Chem / live feeds are available.
  • Deliver a runnable, judge-demoable product within a hackathon timeline, not a research paper.

3.2 Non-Goals (explicitly out of scope for prototype)

  • Running an actual WRF-Chem simulation (requires HPC cluster, days of compute, domain expertise beyond hackathon scope). WRF-Chem is the target production engine, represented in the prototype by a lightweight surrogate coupled model.
  • Full India-wide satellite AQI mapping (that is the ISRO/Bharat Antariksh problem statement's job). AeroSense-Delhi stays Delhi-NCR-first; satellite intelligence (AOD, HCHO, fire hotspots) is an optional enrichment layer, not the core deliverable — this keeps the project aligned with SIH's actual ask rather than diluting it.
  • Real-time SMS/email alert delivery infrastructure at production scale (a stub/logging implementation is sufficient for demo).

6. Functional Requirements

FR-1: Data Ingestion Layer (Adapter Pattern)

The system SHALL ingest weather, pollution, and fire-event data through a single internal interface (DataSourceAdapter), regardless of whether the concrete implementation is MockDataAdapter or LiveDataAdapter. See Section 9 for the full contract.

FR-2: Coupled Forecasting Engine

The system SHALL generate a 72-hour forecast, updated at 3-hour resolution, for:

  • PM2.5, PM10, O₃, NOₓ concentrations
  • Overall AQI (computed per CPCB's national AQI sub-index formula)
  • Temperature, wind speed/direction, PBL height

FR-3: Atmospheric Inversion Module

The system SHALL compute an Inversion Strength Index (ISI) from the vertical temperature profile (or, in mock mode, a synthetic lapse-rate profile) and classify it into Low/Moderate/High/Severe. The ISI SHALL feed into the pollutant-trapping term of the forecasting engine (see Section 11).

FR-4: Stubble-Burning Plume Tracker

The system SHALL model a plume as a set of point-source emissions (from fire-hotspot data — mock or real) that are advected using a Gaussian/Lagrangian dispersion approximation driven by the wind field, producing a plume arrival time and PM2.5 contribution estimate for Delhi NCR.

FR-5: Two-Way Feedback Loop

The system SHALL implement an explicit feedback step each forecast cycle:

  • Weather → Pollution: wind/PBL/inversion modulate dispersion and trapping.
  • Pollution → Weather: aerosol optical thickness (derived from PM2.5) reduces a "surface radiation forcing" term, which lowers next-step PBL height / near-surface temperature.

FR-6: Real-Time Dashboard

The system SHALL display: current AQI, 72-hr AQI forecast chart, pollutant breakdown (PM2.5/PM10/O₃/NOₓ), temperature/wind, PBL height trend, Inversion Strength Index gauge, stubble-plume map with a time slider (Now/+6h/+12h/+24h/+48h/+72h), and a GRAP-stage recommendation banner.

FR-7: Explainability Panel ("Cause → Effect")

For any forecasted spike, the system SHALL generate a plain-language explanation, e.g. "AQI is expected to rise to 410 (Severe) in 18 hours because a stubble-burning plume from [region] is moving toward Delhi under weak 6 km/h winds, combined with a strengthening surface inversion (ISI: High)."

FR-8: Alerts

The system SHALL trigger an alert (in-app + logged webhook/email stub) when forecast AQI crosses CPCB/GRAP thresholds (200/300/400/450).

FR-9: Data Source Configuration & Health

The system SHALL expose an admin view showing, per data type (weather/pollution/fire/satellite), whether it is running in MOCK or LIVE mode, last successful fetch time, and a one-click/one-config-flag toggle per source.

FR-10 (Stretch): Satellite Intelligence Enrichment

If time permits, the system MAY ingest static sample satellite tiles (AOD, HCHO) to enrich the explainability panel with "detected via satellite" source attribution — demonstrating the ISRO-layer synergy without making it the core deliverable.

9. The Mock ↔ Real Data Strategy (Core Design)

This is the architectural answer to "build with mock data now, connect real data later without rework."

9.1 Design Pattern: Adapter + Strategy + Feature Flag

DataSourceAdapter (abstract interface)
 ├── fetch_weather(location, time_range) -> WeatherRecord[]
 ├── fetch_pollution(location, time_range) -> PollutionRecord[]
 ├── fetch_fire_events(region, time_range) -> FireEvent[]
 └── fetch_satellite(region, time_range) -> SatelliteTile[]   # optional/stretch

MockDataAdapter implements DataSourceAdapter      # Phase 1
LiveDataAdapter implements DataSourceAdapter      # Phase 2 (per real source)
   ├── IMDAdapter, CPCBAdapter, ERA5Adapter, VIIRSAdapter, Sentinel5PAdapter

A factory reads a config value per data type and returns the correct adapter:

# config.yaml
data_sources:
  weather: mock        # mock | imd | era5
  pollution: mock       # mock | cpcb | safar
  fire: mock            # mock | viirs
  satellite: mock       # mock | sentinel5p

# factory.py
def get_adapter(source_type: str, provider: str) -> DataSourceAdapter:
    if provider == "mock":
        return MockDataAdapter(source_type)
    return LIVE_ADAPTER_REGISTRY[provider]()

Result: switching from demo to production is a one-line config change per data source — weather can go live while pollution stays mock, enabling incremental rollout as real API access (e.g., CPCB data.gov.in approval) comes through.

9.3 Mock Data Generator — how it stays realistic

  • Seeded using statistical distributions fitted to real historical CPCB/IMD data (e.g., PM2.5 diurnal cycle, wind-speed climatology, Oct–Nov stubble-season spike shape) rather than pure random noise — so demo forecasts look and behave like real Delhi winters.
  • Injects synthetic fire events in a Punjab/Haryana bounding box during a "simulated stubble season," so the plume-tracking and two-way coupling features have something real to react to during the demo.
  • Deterministic seed option, so judges can see the same scenario reproduced, plus a "randomize scenario" button to show robustness.

10.3 Surrogate Coupled Model (replaces WRF-Chem for the prototype)

Since running actual WRF-Chem is infeasible in a hackathon (needs an HPC cluster and hours-to-days per run), the prototype implements a physics-informed surrogate model that reproduces the qualitative and directional two-way coupling behavior WRF-Chem would capture, calibrated against real historical Delhi NCR patterns. This is explicitly documented (in the demo pitch) as "WRF-Chem-ready" — the interfaces below map 1:1 onto what a real WRF-Chem output-ingestion module would provide.

Step-by-step per 3-hour timestep, for horizon t = 0..72h:

  1. Dispersion base term — pollutant concentration is diffused by wind speed (higher wind → more dispersion): dispersion_factor(t) = k1 / (wind_speed(t) + ε)

  2. Inversion trapping term — from Section 11 below, ISI(t) (0–1 normalized) scales up trapped concentration: trapping_factor(t) = 1 + k2 * ISI(t)

  3. Plume contribution — from the Stubble Plume module (Section 12), plume_PM25(t) (µg/m³ arriving from fires).

  4. Combined pollutant forecast: PM2.5(t) = baseline_PM25(t) * dispersion_factor(t) * trapping_factor(t) + plume_PM25(t)

  5. Feedback into weather (Pollution → Weather): radiation_forcing(t) = -k3 * PM2.5(t) // more aerosol, less surface heating PBL_height(t+1) = PBL_height_climatology(t+1) + radiation_forcing(t) // suppressed PBL temperature(t+1) = temperature_climatology(t+1) + k4 * radiation_forcing(t)

  6. Recompute ISI(t+1) using the updated (feedback-adjusted) temperature/PBL — closing the loop for the next timestep.

Constants k1..k4 are calibrated (even approximately) against historical Nov 2023/2024 Delhi CPCB+IMD data so the demo's behavior is directionally realistic, not arbitrary.

11. Inversion Strength Index (ISI) — Calculation Detail

Computed from the vertical temperature profile (vertical_temp_profile_c, surface → ~500m in mock data, or real radiosonde/model levels in production):

lapse_rate = (T_top - T_surface) / height_diff
if lapse_rate > 0:   # temperature increases with height = inversion
    ISI = normalize(lapse_rate, min=0, max=observed_max_lapse)  # 0-1
else:
    ISI = 0  # neutral/unstable, no inversion

Classification:
  ISI < 0.25          -> Low
  0.25 <= ISI < 0.5    -> Moderate
  0.5  <= ISI < 0.75   -> High
  ISI >= 0.75          -> Severe

12. Stubble Plume Dispersion Module

Simplified Gaussian plume / trajectory advection approach (a lightweight stand-in for HYSPLIT/WRF-Chem plume physics):

  1. Each FireEvent (lat, lon, FRP) is treated as a point emission source with strength proportional to frp_mw.
  2. At each timestep, the plume centroid is advected by the current wind vector: new_position = position + wind_vector * Δt.
  3. Plume spreads (Gaussian sigma) grows with distance traveled and inversely with wind speed (calm air → more concentrated but slower-moving plume — consistent with real dispersion physics).
  4. When the plume polygon intersects the Delhi NCR bounding box, an arrival time and estimated PM2.5 contribution are computed and fed into the coupling engine (plume_PM25(t) in Section 10.3).

14. Data Storage Schema (simplified)

-- observations (mock or live, tagged by source_mode)
CREATE TABLE weather_obs (
  id SERIAL PRIMARY KEY, ts TIMESTAMPTZ, station_id TEXT,
  lat FLOAT, lon FLOAT, temperature_c FLOAT, wind_speed_ms FLOAT,
  wind_dir_deg FLOAT, pbl_height_m FLOAT, source_mode TEXT -- 'mock' | 'live'
);

CREATE TABLE pollution_obs (
  id SERIAL PRIMARY KEY, ts TIMESTAMPTZ, station_id TEXT,
  lat FLOAT, lon FLOAT, pm25 FLOAT, pm10 FLOAT, o3 FLOAT, no2 FLOAT,
  source_mode TEXT
);

CREATE TABLE fire_events (
  id SERIAL PRIMARY KEY, ts TIMESTAMPTZ, lat FLOAT, lon FLOAT,
  frp_mw FLOAT, confidence FLOAT, region TEXT, source_mode TEXT
);

CREATE TABLE forecasts (
  id SERIAL PRIMARY KEY, run_ts TIMESTAMPTZ, valid_ts TIMESTAMPTZ,
  zone_id TEXT, pm25 FLOAT, pm10 FLOAT, o3 FLOAT, aqi INT,
  isi FLOAT, pbl_height_m FLOAT, model_version TEXT, source_mode TEXT
);

CREATE TABLE alerts (
  id SERIAL PRIMARY KEY, forecast_id INT REFERENCES forecasts(id),
  triggered_ts TIMESTAMPTZ, threshold_crossed INT, grap_stage TEXT, delivered BOOLEAN
);

(TimescaleDB extension recommended over plain PostgreSQL for efficient time-series queries once real data volume grows.)

19. Success Metrics (for the Prototype / Demo)

  • All 6 SIH mandatory scope items (A–F) demonstrably present and clickable in the live dashboard.
  • Forecast cycle runs end-to-end (data → inversion → plume → coupling → AQI → dashboard) in under 10 seconds.
  • Judges can toggle a data source from Mock → Live-ready in the admin panel and see zero downstream code impact — this is the single strongest technical proof point for the "real data later" claim.
  • Explainability panel produces a coherent, correct cause→effect sentence for at least 3 distinct synthetic scenarios (normal day, stubble spike, deep inversion).

  • Replace surrogate model with full WRF-Chem (production target already implied by architecture).
